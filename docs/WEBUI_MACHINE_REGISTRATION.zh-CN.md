# 分组机器管理部署

## 一次准备，网页登记

此模式用于可信内网。远程执行服务与主监督 Sidecar 由维护人员提前部署，网页不安装软件、不生成令牌、不修改远程权限。运行期间不要修改组和机器配置；系统不做运行中配置锁定。

本分支只支持网页登记。无需设置来源开关，8091 始终代理中央登记接口；中央 SQLite 是唯一机器清单来源。旧机器不自动迁移，不提供旧配置导入；旧文件可以留在磁盘上，但服务不读取它们。已有运行库不会被删除或清空。

中央网关与本机编排进程读取仓库固定位置 `config/workflow-service.json`。首次部署在仓库根目录执行（已有文件直接编辑，勿覆盖）：

```powershell
Copy-Item config/workflow-service.example.json config/workflow-service.json
```

修改统一目录和凭据文件路径，并将 `workflow_db` 指向原中央运行库。相对数据库路径以仓库根目录为基准，与启动目录无关。中央网关和本机编排进程必须使用相同的绝对数据库路径。实际文件被 Git 忽略，示例纳入版本管理；Windows 示例在其他系统部署时需改为对应绝对路径。

配置文件不再接受 `agent_source`、`agents_file`，也不回退到旧部署环境变量；已有的这两个字段必须删除。没有配置文件时可启动并查看空登记，但新增机器前必须准备统一默认值。修改配置文件后重启使用它的服务；机器登记的增改由网页完成，无需重启。远程配置同样使用固定文件名，见下文。

中央登记只需要分组和机器两张表。备份中央 SQLite 即包含机器登记；远程仍不读写 SQLite。先前版本遗留的导入记录表不再使用，不主动删除表或数据。

中央网关配置下列统一默认值，新增机器时保存为该机器配置。后续更改默认值不自动覆盖已登记机器；网页保存机器时会同步当前的 allow_write、allow_full_access，其他默认值不追溯覆盖：

| `machine_defaults` 字段 | 约定 |
| --- | --- |
| `cwd` | 必填，执行机上的默认绝对工作目录，远程需预先创建；节点留空时使用，填写其他绝对目录时覆盖 |
| `protocol` | `ws`（默认）或 `wss`；网页端口指执行服务端口，默认填写 4500 |
| `model` | 默认 `gpt-5.6-sol` |
| `token_env` / `token_file` | 执行服务凭据引用，最多选一项；必须在中央和所有实际派发的远程主监督上能解析为对应执行服务接受的凭据 |
| `sidecar_token_template` | 新增远程主监督必填，中央本地的绝对路径模板，如 `C:\codex-secrets\sidecars\{ip}-{port}.token`；IPv6 的冒号替换为下划线 |
| `allow_full_access` | 默认 `false`；与 `allow_write` 同时为 `true` 时，节点才可选择完全访问（不审批）。修改后重启中央网关，已登记机器通过网页编辑并保存应用；节点权限仍需单独选择 |
| `allow_write` | 默认 `false`；统一允许工作区写入时明确设置 `true`；节点目录覆盖不会改变写权限上限 |

统一的是路径和部署方式。每台主监督的 Sidecar 机器令牌仍必须独立，中央对应文件与该远程机 `sidecar.token_file` 或 `sidecar.token_env` 解析出的值必须匹配。不能多台主监督共用机器令牌，不能与执行服务凭据混用。实际令牌不写入 JSON、数据库配置字段、页面或接口响应。

远程主监督将 `config/workflow-sidecar.example.json` 复制为本机仓库的 `config/workflow-service.json`，填写 `sidecar.gateway_url` 和 `sidecar.token_file`；Windows 直接运行 `scripts/start_workflow_sidecar.ps1`，无需填写启动参数。远程配置不填写 `workflow_db`，仍通过中央接口访问状态。无需填写机器编号：真实身份由中央根据唯一机器令牌确定，启动标签不参与鉴权，不需要登记后再次复制生成的编号。未登记前心跳失败会重试；网页登记后自动识别。不再需要本地执行机清单。

Sidecar 仍只监听 `127.0.0.1:8082`，主监督执行服务的编排工具地址仍为本机 `/mcp`。不要将此端口对外开放。中央以及组内每台主监督必须能通过登记的 IP、端口访问组内执行服务；第一版不维护每个访问来源的不同地址。纯执行机只需已启动执行服务，不要求安装 Sidecar。

## 操作

1. 在 8091 “机器管理”中新建分组。
2. 添加机器，填写 IP、执行服务端口、分组及能力；可以同时选主监督和执行机。页面不接受域名。编号自动生成，名称默认用 IP。
3. 点击“检测连接”。纯执行机验证执行服务协议连接及认证；远程主监督还要求有效 Sidecar 心跳。此操作不创建任务，不验证模型登录额度、业务工作区实际访问或真实业务产出。
4. 检测通过且启用后可提交运行；修改 IP、端口、能力或分组会清除检测结果。在线状态与检测记录分别展示，历史检测通过不保证后续网络始终在线。
5. SOP 选择主监督后，只建议同组执行机。保存时要求机器已登记且能力、分组匹配；提交时额外要求启用并检测通过。网关不可用时无法完成登记模式的 SOP 校验。保存 SOP 需要网关在线。

机器可以编辑和启停，没有物理删除。非空组不能删除；可以编辑机器归属后删除空组。同组不是网络防火墙隔离，只限制平台派发。不同组不能混用于一个 SOP，组内允许多个主监督，主监督固定容量仍为 1。

远程 Sidecar 按需通过认证的 `/internal/v1/agents` 获取本组连接配置，包含执行服务凭据引用，不含实际令牌和 Sidecar 认证引用。不会把清单写回本地文件。中央步骤派发再次检查同组、能力、启用和检测结果，不能以伪造执行机编号越组。

## 首次登记与升级

1. 无活动任务时部署本分支，准备中央与远程的服务配置；已使用上一版服务配置的部署删除 `agent_source`、`agents_file` 字段，以及 8091 中多余的 `codex.agents.source`。
2. 重启中央网关、远程 Sidecar／本机编排进程和配置中心。8090 及纯执行服务无需因机器管理改动重启。
3. 在网页新建分组，重新登记机器并检测。没有旧机器导入入口；旧 SOP 引用未登记编号时，保存和提交都会拒绝，需要重新选择机器。
4. 登记后远程通过中央内部接口按需获取同组机器，不维护独立清单。

## 本机执行

执行方式与机器登记来源是两个概念。本机主监督仍可使用 `local_db`：在中央 `machine_defaults` 中设置 `orchestration_mode` 为 `local_db` 后，通过网页登记本机 IP 和执行端口。此配置只决定新登记／新增监督能力时的默认执行方式，不追溯改变已有机器。本机编排进程直接读取同一 SQLite 的登记信息，不需要 Sidecar 身份令牌。

远程主监督使用默认 `remote_sidecar`，不可访问 SQLite。统一部署参数可省略 `orchestration_mode`。本机文件交接需要额外在统一默认值中设置 `artifact_root` 绝对路径，仍只适用于编排进程与执行服务同机的场景。

## 接口

8091 管理接口由 Java 代理到中央对应去除 `/api` 前缀的路径：

```text
GET/POST   /api/agent-groups
PUT/DELETE /api/agent-groups/{id}
GET/POST   /api/agents
PUT        /api/agents/{id}
POST       /api/agents/{id}/test
```

新建/编辑机器请求包含 `ip`、`port`、`groupId`、`capabilities`、`enabled`；能力为 `supervisor` 和/或 `executor`。机器列表保留旧字段，同时提供分组、IP、端口、检测状态和时间；顶层 `source` 固定为 `registry`。分组请求为 `{"name":"分组名称"}`。

中央 `/agents/validate` 供 Java 保存 SOP 时校验，请求为 `supervisorId` 和 `executorIds`；它不校验检测资格。新增内部 `GET /internal/v1/agents` 沿用机器认证，仅返回认证主监督所属组。

检测业务失败返回 `passed:false` 与普通中文提示，错误类型记入服务日志，不回显底层异常。组/机器输入无效返回 400。管理接口只用于原有受保护内网。

节点工作目录指目标执行机上的绝对路径，需提前准备。已登记机器也支持节点覆盖目录，无需重新登记；更新并重启中央网关后，远程 Sidecar 按需取得新配置。本机编排进程需更新并重启。执行服务自身的文件访问策略仍然有效。
