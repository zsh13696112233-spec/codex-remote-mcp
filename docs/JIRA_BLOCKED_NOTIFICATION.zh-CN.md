# Jira 开发人阻断通知部署与验收

## 升级

1. 按原部署流程备份 MySQL 和中央工作流状态，保留已有迁移记录。
2. 协调升级 Python 网关与所有本机编排进程／远程 Sidecar；全部支持版本 2 后再开始新运行。仅更新线上 SOP 提示词不足以升级实际结果协议。
3. 构建、重启 8091，执行 Flyway V37。旧运行和旧快照不补发通知，已有等待卡片不更换模板；8090 无新增配置要求。
4. 在钉钉卡片平台导入 `config/jira阻断通知卡片.json`，发布专用模板。变量为 `title`（string）、`body`（markdown）、`detailLink`（markdown）；无按钮回调。模板变量缺失或发布失败时不要沿用等待卡片模板。
5. 在机器人页面保存专用模板 ID，确认机器人已加入目标群、应用可见范围和卡片写权限满足要求。在人员页维护 Jira 开发人稳定账号映射；任务定义选择阻断通知群。

账号选择必须与实际 Jira 返回一致：优先 accountId，其次 key、name，不把显示名当账号。配置页面不提供自动匹配或群成员推断。专用通知通过应用凭证投递，不依赖临时聊天回复地址；详情链接沿用配置中心生成的监控地址，应确保收件人可访问。

## 验收

先在机器人页面选择已启用的群、人员和测试文案发送测试卡片。观察运行通知详情中的已投递状态，并在钉钉核验卡片排版、群成员 @ 和详情入口；接口成功不能代替真实提醒验收。页面重复提交或请求超时后重试应保持相同测试编号。

此前指定的验收对象是“APP新版BI统计”群、朱家丰，文案“DFW-9826 已阻断，请补充服务端源码”。必须先确认准确 Jira 账号、群成员身份、应用权限和已发布模板。本次代码测试使用虚构对象，未发送该真实通知。

使用新运行分别从网页、定时和钉钉启动；关闭普通主动通知，确认阻断时仍发任务配置群，接收人始终是开发人。验证无任务、用户取消、普通执行失败均不触发；开发人空值、多人、无映射、停用对象和模板缺失显示明确原因。角色修改或 Jira 评论失败仍结束流程并通知。

## 故障与恢复

发送状态持久化，普通事件重复和应用重启不会创建第二条记录。只有获取发送凭证前的失败、明确未发送的认证或限流响应允许有限重试；网络超时、服务异常和无法核对的回执保留“结果未确认”。发送中记录超过两分钟未完成也转为结果未确认，不重新投递。

当前没有接入可证实指定群投递结果的查询 API；请先核查群内是否已有卡片，不能仅凭实例存在认定已投递。系统不提供一键强制重发或换人补发，以避免结果不明时重复提醒。已确认为无法通知的历史记录不会在修改映射或模板后自动补发；修正后用新运行或新测试验收。

H2 MySQL 模式验证迁移和持久化行为；正式 MySQL 8、真实 Jira、远程部署与钉钉平台投递需要在目标环境另行验收。三个服务仍只供可信内网访问，不增加公网入口。
