# Jira 开发人完成与阻断通知部署及验收

## 升级

1. 按原部署流程备份 MySQL 和中央工作流状态，保留已有迁移记录。
2. 协调升级 Python 网关与所有本机编排进程／远程 Sidecar；全部支持版本 2 后再开始新运行。仅更新线上 SOP 提示词不足以升级实际结果协议。
3. 构建、重启 8091，执行 Flyway V37。旧运行和旧快照不补发通知，已有等待卡片不更换模板；8090 无新增配置要求。
4. 在钉钉卡片平台导入 `config/jira阻断通知卡片.json`，发布专用模板。变量为 `title`（string）、`body`（markdown）、`detailLink`（markdown）；无按钮回调。模板变量缺失或发布失败时不要沿用等待卡片模板。
5. 在机器人页面保存专用模板 ID，确认机器人已加入目标群、应用可见范围和卡片写权限满足要求。同步钉钉人员（开发人通知不要求人员启用）；任务定义选择开发人通知群。

通知按开发人显示名精确匹配钉钉人员，同名固定取一个，具体规则见[配置中心说明](../services/role-task-config-center/README.md#jira-开发人阻断通知)。不再维护 Jira 人员映射。专用通知通过应用凭证投递，不依赖临时聊天回复地址；详情链接沿用配置中心生成的监控地址，应确保收件人可访问。

## 验收

先在机器人页面选择已启用的群、通讯录可用的人员并填写测试文案发送测试卡片。观察运行通知详情中的已投递状态，并在钉钉核验卡片排版、群成员 @ 和详情入口；接口成功不能代替真实提醒验收。页面重复提交或请求超时后重试应保持相同测试编号。

此前指定的验收对象是“APP新版BI统计”群、朱家丰，文案“DFW-9826 已阻断，请补充服务端源码”。必须先确认准确 Jira 开发人显示名、钉钉人员身份、应用权限和已发布模板。本次代码测试使用虚构对象，未发送该真实通知。

使用新运行分别从网页、定时和钉钉启动；关闭普通主动通知，确认阻断时仍发任务配置群，接收人始终是开发人。全自动成功时确认发送完成卡片并 @ 对应人员，普通结束汇总保持独立。验证无任务、用户取消、普通执行失败及半自动成功不触发完成通知；开发人空值、多人、无同名人员、人员通讯录不可用、群或机器人停用和模板缺失显示明确原因。角色修改或 Jira 评论失败仍结束流程并通知。

## 故障与恢复

### V37 时间戳默认值错误

若 V37 创建 `codex_blocked_notifications` 时出现 `Invalid default value for 'updated_at'`，先只读检查数据库设置与迁移状态：

```sql
SELECT VERSION(), @@SESSION.explicit_defaults_for_timestamp, @@SESSION.sql_mode;
SELECT version, description, success FROM flyway_schema_history WHERE version = '37';
```

关闭显式时间戳默认值且启用严格零日期检查时，第二个未指定默认值的非空 TIMESTAMP 会产生非法零日期默认值。修正后的 V37 为 `next_at` 和 `updated_at` 显式指定 `DEFAULT CURRENT_TIMESTAMP(6)`，不加自动更新时间规则；业务代码仍显式写入时间，轮询只更新 `next_at`。

此修正仅用于 V37 尚未成功应用的环境。已经成功应用原 V37 的数据库不能直接换用修改后的迁移，否则会发生校验和不一致；应保留原 V37，通过新的迁移演进，不能用 repair 掩盖历史差异。

MySQL 的 DDL 可能已部分提交：任务群字段、模板表及默认行、人员映射表可能已存在。只清除失败记录后重启会再次遇到字段或表重复，新增 V38 也不能越过失败的 V37。停止配置中心并备份后，先核对实际表结构、迁移记录和是否存在业务数据，再制定恢复步骤。仅在确认是无业务数据的开发环境且用户明确授权后，才可清理本次失败产生的对象和 V37 失败记录；不要清库、清除其他迁移记录或关闭 Flyway 校验。

恢复完成后，Windows 从仓库根目录执行 `mvn -f services/role-task-config-center/pom.xml clean test`（macOS 用 `mvnd`），再启动配置中心，避免继续使用 `target/classes` 中的旧脚本。H2 不复现 MySQL 的隐式零日期规则，仍需目标 MySQL 验证。

### 通知投递恢复

发送状态持久化，普通事件重复和应用重启不会创建第二条记录。只有获取发送凭证前的失败、明确未发送的认证或限流响应允许有限重试；网络超时、服务异常和无法核对的回执保留“结果未确认”。发送中记录超过两分钟未完成也转为结果未确认，不重新投递。

当前没有接入可证实指定群投递结果的查询 API；请先核查群内是否已有卡片，不能仅凭实例存在认定已投递。系统不提供一键强制重发或换人补发，以避免结果不明时重复提醒。已确认为无法通知的历史记录不会在修改人员或模板后自动补发；修正后用新运行或新测试验收。

H2 MySQL 模式验证迁移和持久化行为；正式 MySQL 8、真实 Jira、远程部署与钉钉平台投递需要在目标环境另行验收。三个服务仍只供可信内网访问，不增加公网入口。

### 显示名通知升级

更新 Python 网关及实际执行的本机 MCP / 远程 Sidecar，使提示词要求返回真实开发人显示名；重新构建并重启配置中心、刷新页面。无数据库迁移，沿用已有卡片模板。映射页面及读写 API 已移除，旧映射数据不清理、不使用。不自动修改线上自定义角色、不重跑任务、不补发已结束通知；已有 pending 通知按冻结收件人投递。检查线上角色是否仍要求用用户名或拼音替代显示名，并在新运行验收成功、阻断、无任务及无法匹配的行为。只向配置群发卡片并 @，不检测人员是否在群、不转单聊，接口投递成功不代表目标人员收到提醒。

开发人通知忽略人员启用开关：姓名匹配、投递前检查和专用测试均允许通讯录可用的未启用人员。普通通知对象选择规则不变，通知群和机器人仍须启用。此项仅需重新构建并重启 8091 并刷新页面，无需更新 Python、数据库或卡片模板；历史已记录“无法通知”的运行不自动补发。
