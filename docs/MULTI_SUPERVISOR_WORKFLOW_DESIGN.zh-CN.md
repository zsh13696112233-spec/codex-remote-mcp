# 多主监督机工作流设计

> 状态：阶段 A、B 已实现；真实多机验收待目标环境执行。
> 更新日期：2026-09-02。
> 本文同时记录当前实现边界和后续演进方向。

## 一、目标与确定约束

平台需要从当前“所有 SOP 固定使用 `local` 主监督”的模式，演进为由一个配置中心统一管理、多个主监督机并行工作的模式。

当前实现确定以下约束：

- 全系统部署一个 `8091` 角色任务配置中心，负责角色、SOP、任务定义、不可变运行快照和控制操作。
- 全系统保留一个逻辑上的中央 `8080` Python 工作流网关，负责运行状态、分配、租约、事件和聊天。
- 全系统保留一个 `8090` 监控中心，通过中央 `8080` 查看任意单个 `workflowId`。
- 阶段 A 支持同机多 app-server；阶段 B 支持不同 IP 的远程主监督 app-server 与本机 HTTP Sidecar。
- 每个主监督同一时间最多承担一个活动工作流。
- 每个 SOP 选择一个主监督执行机；不同 SOP 可以选择不同主监督并同时运行。
- 每个业务步骤继续独立保存执行机和可选工作目录；系统不要求同一 SOP 的步骤使用相同执行机或目录。
- 不同 SOP 的工作目录由部署和配置约定保持隔离；第一阶段不做跨 SOP 目录冲突检测。
- 多个 SOP 可以在同一台物理执行服务器上并行，运维侧负责为它们分配不同目录并确认服务器容量足够。
- 阶段 B 不实现跨机器步骤文件传输；远程主监督只允许运行 `legacy_text`，`cumulative_files` 在提交时拒绝。
- 节点仍按 `dependsOn` 严格执行；配置中心继续只生成严格串行 SOP，失败策略仍固定为 `stop`。
- Skill/MCP 字段继续只是配置标签，不因本设计自动安装、启用或授权。

本文中的“主监督容量为 1”表示同一主监督机最多绑定一个尚未进入终态的工作流，不等同于整个系统只能运行一个工作流。

## 二、推荐拓扑

```text
                                 ┌─▶ 主监督 A（IP-A，容量 1）─┐
浏览器 / 飞书 / 钉钉             │                            │
          │                      │                            ▼
          ▼                      │                      执行服务器 X
8091 角色任务配置中心 ─▶ 8080 中央运行网关                  ├─ /workspaces/sop-a
          │                      │                      ├─ /workspaces/sop-b
          │                      │                      └─ /workspaces/sop-c
          │                      └─▶ 主监督 B（IP-B，容量 1）─┘
          │
          └─▶ 8090 监控地址
                    │
                    └────────────▶ 8080 中央运行网关
```

推荐只部署一个逻辑上的中央网关，不为每台主监督机各部署一套独立网关。

### 1. 控制中心侧

控制中心环境部署：

- `8091`：配置与控制平面。
- `8090`：查询与消息代理平面。
- `8080`：统一运行时入口。
- MySQL 8：保存 `8091` 的配置数据和运行快照。
- SQLite：第一阶段继续保存 `8080` 的运行状态；只允许中央网关进程直接访问。

三个服务可以位于同一台主机，也可以拆开部署，但 `8091` 和 `8090` 始终只配置一个中央 `CODEX_GATEWAY_URL`。

### 2. 每台主监督机

阶段 B 的每台远程主监督机部署：

- 一个 Codex app-server，通常监听可信内网 `4500`。
- 一个只监听 `127.0.0.1:8082` 的 Orchestrator HTTP Sidecar。
- 指向中央 `8080` 内部 API 的地址和机器身份凭据。
- 可调度业务执行机的地址或从中央网关取得的脱敏调度信息。

主监督机不部署完整的 HTTP 工作流网关，也不保存独立的工作流数据库。

远程 app-server 使用 `[mcp_servers.codex_orchestrator] url = "http://127.0.0.1:8082/mcp"` 连接官方 Streamable HTTP MCP。Sidecar 通过独立 Bearer Token 调用中央内部 API，不读取或复制 SQLite；中央网关连接 app-server 的令牌与 Sidecar 机器令牌互相独立。阶段 A 的本机兼容 MCP 继续允许与中央网关共享 SQLite。

### 3. 执行服务器

执行服务器部署一个 Codex app-server。不同 SOP 使用不同目录，例如：

```text
SOP A → worker-main → /srv/codex-workspaces/sop-a
SOP B → worker-main → /srv/codex-workspaces/sop-b
```

同一 SOP 的步骤按依赖串行执行。步骤工作目录留空时继承所选执行机默认目录；不同 SOP 的目录隔离由部署约定保证。

## 三、为什么使用一个中央网关

如果每台主监督机都部署独立网关和 SQLite，会引入以下问题：

- `8091` 必须维护多个网关地址，并为每次运行记录路由目标。
- `8090` 查询、事件、消息、取消和重跑前必须先解析工作流属于哪个网关。
- 执行机列表、工作流状态和并发额度分散，难以统一校验。
- 网关离线后，中央系统难以统一判断租约和恢复状态。
- 重试原快照、使用最新配置运行和机器人绑定都会增加跨网关路由分支。

中央 `8080` 可以保持现有公共边界：

```text
8091 / 8090 → 8080 → 主监督与执行机
```

Java 系统仍不直接调用 MCP、Python 脚本或 app-server WebSocket。

## 四、运行链路

一次正常运行按以下顺序进行：

1. 用户在 `8091` 运行任务定义。
2. `8091` 使用最新 SOP 生成不可变提交快照，其中包含 `supervisorAgentId`、步骤执行机和工作目录。
3. `8091` 调用中央 `8080` 的 `POST /workflows`。
4. `8080` 校验主监督与步骤执行机是否存在、启用、能力匹配，并保留现有权限档位校验；不要求步骤执行机或工作目录一致。
5. `8080` 原子占用所选主监督；如果主监督忙，工作流进入等待队列。
6. 主监督空闲后，`8080` 在对应 app-server 创建主监督会话。
7. 主监督调用现有 Orchestrator MCP 决定派发下一步骤；远程主监督通过本机 `8082/mcp` 调用相同工具。
8. 本机兼容 MCP 通过共享 SQLite 读取状态；远程 Sidecar 通过中央 `/internal/v1` 读取上下文并执行带租约的原子准备派发。
9. MCP 连接业务执行机 app-server，在步骤指定或默认工作目录中创建执行会话。
10. 本机 MCP 直接写共享 SQLite；远程 Sidecar 使用当前租约令牌同步状态并幂等批量上报事件，由中央网关写入 SQLite。
11. 所有步骤完成、失败或任务取消后，`8080` 进入终态并释放主监督租约。

“由主监督控制执行机”表示步骤派发决策来自主监督；依赖校验、租约、状态转换和审计仍由中央网关确定性执行。

## 五、SOP 配置模型

### 1. 主监督选择

`8091` 从中央 `8080` 的执行机能力接口读取主监督建议列表，但输入框允许填写任意非空 ID。网关离线或 ID 暂时不在列表中不影响保存；`8091` 只校验非空和长度，不校验在线状态、启停状态或能力。SOP 保存：

```json
{
  "supervisorAgentId": "supervisor-a"
}
```

`8091` 只保存稳定执行机 ID，不保存或回显 IP、WebSocket 地址、令牌和内部会话信息。

远程主监督在中央 `agents.json` 中使用如下结构：

```json
{
  "agents": {
    "supervisor-a": {
      "url": "wss://supervisor-a.internal/codex",
      "capabilities": ["supervisor"],
      "capacity": 1,
      "token_env": "SUPERVISOR_A_APP_SERVER_TOKEN",
      "orchestration_mode": "remote_sidecar",
      "sidecar_token_env": "SUPERVISOR_A_SIDECAR_TOKEN"
    },
    "worker-main": {
      "url": "wss://worker-main.internal/codex",
      "capabilities": ["executor"],
      "allow_cwd_override": true
    }
  }
}
```

`orchestration_mode` 缺省为 `local_db`，保持旧配置兼容。`remote_sidecar` 必须具备 `supervisor` 能力，并在 `sidecar_token_env` 与 `sidecar_token_file` 中严格选择一个；后者必须是中央网关机器上的绝对路径。能力字段是运行时白名单；`capacity` 当前只用于主监督容量，不得与仅作标签的 Skill/MCP 字段混用。

### 2. 执行机和工作目录

现有数据模型继续在每个步骤上保存执行机和工作目录。配置中心使用 `/api/agents` 提供填写建议，但允许保存列表之外的非空执行机 ID，也不要求同一 SOP 的步骤使用相同执行机或目录。

工作目录可以留空；留空时继承执行机在 `agents.json` 中配置的默认目录。填写覆盖目录时，运行时继续执行现有绝对路径、`allow_cwd_override` 和写权限校验。阶段 A 不增加 SOP 级目录规范化或一致性校验。

不同 SOP 不使用相同或互相嵌套的目录是第一阶段的部署约定。配置和运行时不扫描其他 SOP，也不创建跨 SOP 工作区租约；如果后续出现目录复用或冲突，再单独增加运行时互斥机制。

### 3. 更换执行机

SOP 可以在后续编辑中改用其他执行机或工作目录，但运行遵循不可变快照：

- 已经运行中的工作流继续使用原快照，不中途迁移。
- 使用最新配置创建的新运行使用新的执行机和工作目录。
- 按原运行快照重试时继续使用快照中的执行机 ID 和工作目录。
- 如果必须切换正在运行的任务，应取消原任务，再使用最新配置创建新的 `workflowId`。

快照冻结的是执行机 ID，不是 `agents.json` 中当前解析出的 IP。为了保持历史语义，执行机更换地址时应创建新 ID，例如：

```text
worker-a-v1 → 192.168.1.101
worker-a-v2 → 192.168.1.102
```

不要复用旧 ID 修改为含义不同的新机器，否则按原快照重试也会解析到新地址。

## 六、主监督容量与持久化租约

### 1. 容量定义

每个主监督的第一阶段容量固定为 `1`：

- 一个主监督同一时间最多租用给一个 `running` 或 `cancelling` 工作流；其他 `queued` 工作流不持有租约。
- 半自动流程处于倒计时或人工暂停时，工作流仍占用主监督。
- 工作流进入 `completed`、`failed` 或 `cancelled` 后释放主监督。
- 失败提案、重复确认和普通查询不创建第二个工作流租约。

任务助手属于工作流的辅助会话，不创建新的工作流占用。如果部署要求同一主监督机器连 Codex turn 也只能并发一个，则需要把任务助手加入同一执行队列；这与“一个活动工作流”是两个不同的容量维度，实施时不得混淆。

### 2. 租约模型

当前 `asyncio.Lock` 只保护单个 Python 进程中的单次任务，不能代表完整工作流。阶段 A 在运行存储中增加最小化持久租约：

```text
supervisor_id       主键
workflow_id         唯一，当前占用的工作流
leased_at           首次占用时间
```

行为要求：

- 提交成功后工作流保持 `queued`，调度器以事务和唯一约束领取空闲主监督，并把领取项转为 `running`。
- 同一主监督繁忙时，后续工作流按 `created_at + workflow_id` 稳定排队。
- 释放租约和工作流进入终态应属于同一事务边界，避免永久占用或重复派发。
- 取消和重跑继续使用 `stateVersion` 防止并发确认覆盖新状态。
- 半自动暂停继续占用租约；独立任务助手不占用额外工作流租约。
- 网关启动时把遗留 `running/cancelling` 工作流直接标记为失败，清除租约并继续调度排队项，不重新附着或中止旧外部会话。

阶段 B 为远程租约增加 `sidecar_instance_id`、不可预测 `lease_token`、`renewed_at` 和 `expires_at`，并持久化当前及已退役的 Sidecar 实例。Sidecar 每 5 秒心跳一次，租约以最后一次权威心跳为基准在 20 秒后过期。所有远程写入在同一个 `BEGIN IMMEDIATE` 事务中同时校验主监督归属、当前实例、令牌和过期时间；实例更换后，已退役实例不能通过旧心跳重新登记，也不能用旧租约回写。

远程主监督从未上线或心跳已过期时，新提交工作流直接进入 `failed`，不会等待机器上线。运行中的远程主监督失联、Sidecar 实例更换或租约过期时，中央网关在事务中把工作流标记失败并释放租约，不自动迁移活动 turn。本机 `local_db` 主监督继续使用轻量 WebSocket 探测；网关重启仍沿用阶段 A 的活动工作流直接失败语义，不做可靠重新附着。

## 七、执行服务器并发与工作目录约定

多台主监督可以同时控制同一台物理执行服务器。第一阶段不实现执行服务器容量调度、跨 SOP 目录冲突检测或工作区租约，按以下简单约定运行：

- 同一 SOP 严格串行，同一时刻最多执行一个业务节点。
- 不同步骤可以配置不同逻辑执行机 ID、不同目录或空目录，中央网关不做一致性校验。
- 不同 SOP 的目录由部署人员预先隔离，不使用相同或互相嵌套的目录。
- 执行服务器可承受的并发量由部署和运维配置保证，中央网关不在第一阶段分配执行机并发槽。
- 中央网关仍负责依赖校验、节点状态和主监督租约，但不追踪执行服务器的物理容量或活动目录。

如果后续允许不同 SOP 复用目录，或实际出现执行服务器过载，再单独设计执行机容量和工作区租约，不纳入本阶段。

快速验证阶段也可以为不同工作区配置不同逻辑执行机 ID，即使它们指向同一 app-server：

```json
{
  "worker-sop-a": {
    "url": "wss://worker-main.internal/codex",
    "cwd": "/srv/codex-workspaces/sop-a"
  },
  "worker-sop-b": {
    "url": "wss://worker-main.internal/codex",
    "cwd": "/srv/codex-workspaces/sop-b"
  }
}
```

该方式既可用于验证，也可作为第一阶段的部署配置方式；它不表示中央网关能够识别这些逻辑 ID 是否指向同一台物理服务器。

## 八、运行状态存储演进

### 1. 第一阶段保留 SQLite

第一阶段只有一个中央 `8080` 时可以继续使用 SQLite：

- 只有中央网关直接打开数据库文件。
- 远程主监督和 Sidecar 不直接访问数据库。
- 使用 WAL、事务、唯一约束和现有 `busy_timeout` 处理中央进程内并发。
- 网关与本机兼容 MCP 使用完全相同的 `CODEX_WORKFLOW_DB` 绝对路径。

本机兼容 MCP 仍可直接打开共享 SQLite；不同 IP 的远程 Sidecar 已改为使用受保护的中央内部 API。

阶段 B 的 `/internal/v1` 已覆盖以下能力：

- 读取工作流和节点调度上下文。
- Sidecar 心跳、实例登记和租约续期。
- 原子领取主监督租约和准备待执行节点。
- 校验依赖和当前状态版本。
- 同步步骤任务状态、结果和错误。
- 使用工作流内幂等键批量写入事件。

内部 API 不是浏览器接口，不得暴露到普通前端，也不得返回其他工作流的执行机地址、令牌或底层 thread/turn 标识。Bearer Token 唯一映射到一个主监督，工作流写操作额外要求 `X-Workflow-Lease`。固定错误语义为认证失败 `401`、跨主监督访问 `403`、对象不存在 `404`、旧实例/旧租约/状态冲突 `409`。

### 2. 迁移到 MySQL 的时机

以下任一需求出现时，应把运行状态迁移到 MySQL 8 或 PostgreSQL：

- 部署两个或更多 `8080` 网关实例。
- 需要网关高可用和自动故障转移。
- 工作流、事件和聊天写入量超过单机 SQLite 的可接受范围。
- 需要数据库级分布式租约、行锁和更强的运维能力。

如果选择 MySQL，推荐使用独立数据库和账号：

```text
codex_config             8091 配置数据
codex_workflow_runtime   8080 运行状态
```

可以使用同一个 MySQL 8 实例，但必须保持所有权边界：

- `8091` 不直接修改运行时数据库。
- `8090` 不连接任何配置或运行数据库。
- 远程主监督不持有数据库账号，只调用中央 `8080` 内部 API。
- Python 运行时使用独立迁移机制演进表结构，并兼容已有 SQLite 数据迁移。

仅为多主监督部署不要求立即迁移 MySQL；单中央网关模式应先完成 API 隔离，再按容量和高可用需求迁移。

## 九、结果交接与文件边界

第一阶段不实现跨机器文件传输：

- 提交协议允许不同步骤选择不同执行机，但这不代表文件可以跨机器交接。
- 后续步骤只有在任务要求明确且文件在同机受控目录可用时才读取前序产物。
- 跨机器 `cumulative_files`、对象存储、下载上传和远程 `artifact_root` 不在第一阶段范围内。
- 需要纯文本结果交接时使用兼容的 `legacy_text` 语义。
- 需要在共同工作目录中交接文件时，提示词应明确文件名和用途；运行时不扫描整个业务工作区。

未来如果允许一个 SOP 的步骤分布到不同执行机，再单独设计对象存储或受控附件传输协议。

## 十、故障语义

| 场景 | 第一阶段建议行为 |
| --- | --- |
| 所选主监督忙 | 工作流保持排队，等待该主监督，不静默切换 |
| 所选主监督连接失败 | 本次工作流标记失败，释放租约并继续调度下一项，不等待机器上线 |
| 远程主监督从未上线或当前离线 | 新工作流立即失败，不排队等待机器上线 |
| 远程主监督运行中失联或 Sidecar 更换实例 | 20 秒内标记失败并释放租约，不自动迁移活动 turn |
| 执行机离线 | 当前步骤失败或中断，保留可诊断信息 |
| 不同 SOP 被错误配置到冲突目录 | 第一阶段不自动检测；停止相关任务并修正部署配置 |
| 8080 重启 | 遗留活动工作流直接标记失败并清除租约，然后继续排队项；不重新附着旧外部会话 |
| 8090 离线 | 不影响运行，恢复后按 `workflowId` 查询 |
| 8091 离线 | 已提交工作流继续运行，恢复后刷新状态 |

第一阶段不做进行中工作流的主监督自动故障转移。因为 thread、turn、MCP 上下文和已执行副作用不能仅靠更换 IP 安全恢复。

## 十一、网络与安全

分布式部署后，`0.0.0.0` 仅表示绑定所有接口，不代表允许公网访问。必须配置：

- `8091`、`8090` 只对可信用户网络或受保护反向代理开放。
- `8080` 只允许 `8091`、`8090` 和主监督 Sidecar 访问。
- 主监督 app-server 只允许中央 `8080` 访问。
- 执行机 app-server 只允许受信任的主监督 Sidecar 或中央调度端访问。
- 跨机器 app-server 使用 WSS、专用内网或安全隧道，不在不可信网络裸用 `ws://`。
- 内部 API 使用每台机器独立的身份令牌或 mTLS，支持吊销和轮换。
- 令牌只通过 `token_env`、网关本机绝对路径 `token_file` 或密钥管理系统提供，不写入 SOP、运行快照或前端响应；`token_env` 与 `token_file` 严格二选一。
- 页面和普通用户消息不得暴露 IP、令牌、thread、turn、原始事件或内部错误。
- 防火墙按来源 IP 和必要端口做最小授权，不直接把 `8080`、`8090`、`8091` 或 app-server 暴露公网。
- Sidecar `8082` 只绑定回环地址，不开放防火墙；阶段 B 使用每主监督独立 Bearer Token，mTLS 留到后续阶段。

## 十二、阶段 A/B 实施决策

阶段 A 按以下决策实施：

1. 配置中心后端和前端删除 `supervisorAgentId=local` 保存硬编码，新建 SOP 仍默认填写 `local`。
2. `SopSaveRequest` 正式接收 `supervisorAgentId`，只做非空和长度校验。
3. `/api/agents` 只提供填写建议，不能成为保存配置的在线依赖。
4. Flyway `V2__use_local_supervisor.sql` 曾把历史数据统一迁移为 `local`；现有列可以直接复用，不修改 V2，也不新增迁移。
5. Python 网关在持久化前权威校验主监督和步骤执行机的存在、启停、能力及权限档位。
6. SQLite 最小租约替代进程内锁作为“一个主监督一个活动工作流”的权威状态。
7. 独立任务助手使用独立 Orchestrator，不计入工作流租约。
8. MCP 当前直接使用共享 SQLite，远程主监督无法访问中央主机本地文件。
9. `8091` 和 `8090` 当前各自只配置一个 `CODEX_GATEWAY_URL`；这正是保留单中央网关的基础。
10. 飞书与钉钉当前全局最多一个机器人任务；多主监督第一阶段不自动取消该限制。

阶段 B 在上述边界上增加：

1. 每台远程主监督只部署 app-server `4500` 和回环 Sidecar `8082`，不部署网关或运行数据库。
2. 中央网关仍直接连接主监督 app-server；主监督通过本机 Streamable HTTP MCP 调用 Sidecar，Sidecar 再连接步骤执行机。
3. Sidecar 机器令牌和 app-server 连接令牌独立配置，令牌来源支持环境变量或绝对文件且每次请求重新读取。
4. 心跳周期固定 5 秒，20 秒未续租即离线；活动任务失败释放，不等待、不迁移。
5. Sidecar 实例变更立即使旧实例和旧租约失效；所有远程状态写入在 SQLite 事务内执行租约栅栏校验。
6. 远程工作流只支持 `legacy_text`，不上传、下载或回传跨机器附件。
7. 阶段 B 继续保持单中央网关和 SQLite；mTLS、多网关高可用和活动 turn 故障转移不在本阶段。

## 十三、分阶段实施建议

### 阶段 A：配置和单机并发验证

- 为执行机配置增加明确的主监督/执行者能力，并为主监督增加容量信息。
- 扩展 `/agents` 的脱敏响应，返回启停、能力、固定主监督容量、缓存的轻量可达性和基于租约的忙闲状态，不返回地址、认证信息或原始连接异常。
- 在 `8091` SOP DTO、领域模型、JSON 映射和页面增加主监督选择。
- 删除保存路径中的 `local` 硬编码，保留历史缺省值兼容。
- 将主监督 ID、执行机 ID 和工作目录冻结到新运行快照。
- 在同一台主机用两个不同 app-server 端口模拟 `supervisor-a`、`supervisor-b`，验证两个 SOP 并行。
- 增加主监督容量为 1 的持久租约和排队测试。

### 阶段 B：远程主监督（已实现）

- 已定义中央 `/internal/v1`、每主监督独立 Bearer Token 和工作流租约头。
- 已把远程 MCP 的节点读取、原子准备派发、状态和事件写入改为中央 API。
- 已增加 5 秒权威心跳、20 秒租约超时、实例历史和旧写防护。
- 已提供 `workflow_sidecar.py`、PowerShell 启动脚本、中央与远程配置示例以及 Streamable HTTP MCP 配置。
- 自动测试覆盖身份隔离、状态码、实例替换、租约过期、事件重试幂等和旧 SQLite 升级。
- 两台不同 IP 主监督与共享执行机的真实部署验收仍需在目标环境执行。

### 阶段 C：共享执行服务器验证

- 按部署约定为不同 SOP 分配不同工作目录，验证它们可以并行运行。
- 记录执行服务器容量由运维保证，不增加并发槽或工作区租约。
- 验证同一 SOP 的步骤使用不同执行机、不同或空目录时，系统不会因一致性规则拒绝提交。
- 验证 SOP 修改执行机只影响使用最新配置创建的新运行。
- 验证按原快照重试仍使用原执行机 ID 和工作目录。

### 阶段 D：运行数据库和高可用

- 根据真实负载决定是否迁移到独立 MySQL 运行库。
- 建立 Python 运行时迁移和 SQLite 数据迁移工具。
- 将租约、心跳、事件游标和状态转换放入明确事务。
- 数据库迁移稳定后再考虑多个 `8080` 实例和负载均衡。

## 十四、验收标准

- `8091` 可以为不同 SOP 填写不同主监督；网关离线或 ID 未知时仍可保存，真正提交时由 `8080` 拒绝无效配置。
- SOP A 与 SOP B 分别选择不同主监督时可以同时运行。
- 同一主监督同一时间只绑定一个活动工作流，后续任务稳定排队且不会重复启动。
- 主监督租约在完成、失败和取消后准确释放，网关重启后不会把同一主监督分配给两个工作流。
- 同一 SOP 的步骤可以使用不同执行机、不同或空目录；空目录继承执行机默认值。
- 按部署约定使用不同目录的 SOP，可以在同一物理执行服务器上并行。
- 第一阶段明确不承诺自动检测或阻止跨 SOP 的相同、嵌套目录配置。
- 已运行快照不受后续 SOP 修改影响；最新配置运行和原快照重试语义明确。
- 阶段 B 的远程主监督不得直接读取数据库文件，也不得持有中央运行数据库账号。
- 远程主监督只支持 `legacy_text`；`cumulative_files` 在运行持久化前稳定拒绝。
- 停止远程 Sidecar 后，活动工作流在 20 秒内失败释放，旧实例不能回写；恢复后的新实例可以接收新任务。
- `8090` 继续只按 `workflowId` 展示一个工作流，不增加编辑或直接重试控制能力。
- 用户页面和消息不泄露 IP、令牌、内部会话标识或原始事件。
- 第一阶段不声称支持跨机器文件交接、主监督自动故障转移或多网关高可用。

## 十五、非目标

第一阶段明确不包含：

- 通用 DAG 编辑器。
- 一个主监督同时编排多个活动工作流。
- 进行中工作流自动迁移到其他主监督。
- 跨执行机附件传输、对象存储或远程 `artifact_root`。
- 每台主监督独立部署工作流网关和数据库。
- 多个 `8080` 实例的高可用集群。
- 执行服务器物理容量调度、跨 SOP 目录冲突检测和工作区租约。
- 自动安装或授权 SOP 中配置的 Skill/MCP。
- 自动放开飞书或钉钉的全局单机器人任务限制。

以上能力如需扩展，应在第一阶段稳定后另行设计公共契约、状态迁移和验收标准。
