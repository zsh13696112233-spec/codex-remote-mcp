## 审查发现（业务代码尚未修复）

### P2：失败重试破坏钉钉消息顺序（已复现）

位置：`services/role-task-config-center/src/main/java/com/codexflow/configcenter/integration/dingtalk/DingTalkOutboxRepository.java:37`，`DingTalkStore.java:728`，`DingTalkBotCoordinator.java:177`。
查询只领取当前到期记录，然后按 delivery_order 排序。第一条失败进入退避时，后续记录仍可领取；同批领取后的发送循环也不会因前一条失败停止。因此用户可先收到“步骤完成”，稍后收到“步骤开始”，长文本分段也可能错序。
临时 H2 回归测试：入队开始消息、领取并标记失败、入队完成消息；断言后续不能被领取，实际返回完成消息，1 项失败符合预期。复现源码保留为 `history/ReviewOrderingRegressionTest.java`，已从正式测试目录和编译输出移走。
建议：明确同工作流/会话的顺序范围，领取及发送均不能越过该范围内未送达前项，同时避免一个坏会话阻塞所有任务。

### P2：多轮图片返工累积超过派发上限，确认时仍扣额度（已复现）

位置：`services/python-workflow/src/workflow_store.py:2421`、`workflow_input_images.py:173`、`codex_orchestrator_mcp.py:973`。
每次返工只追加图片关联，步骤读取所有历史 action 的图片；每条新消息只验证自身 20 MB，但实际派发验证累计 20 MB。两轮各约 11 MB 的合法图片请求均确认成功，已用额度为 2，步骤累计 22,000,178 字节后派发失败。旧图没有可撤销/替换的当前集合，之后纯文字返工也无法降低累计容量。
复现：`PYTHONPATH=services/python-workflow/src:services/python-workflow .venv/bin/python history/reproduce_image_budget.py`。使用临时 SQLite 和合成 PNG；在网络请求前复现，不调用真实执行机。
建议：将当前有效图片与审计历史分开，明确替换/继承语义；确认事务之前验证每个受影响步骤最终图片总量，失败不得先消耗返工额度。

### P2：网页重跑同一已结束工作流后，钉钉停止跟踪（静态调用链确认）

位置：`services/role-task-config-center/src/main/java/com/codexflow/configcenter/integration/dingtalk/DingTalkStore.java:479`。
终态且 waitingAssistant=false 的绑定被永久排除轮询。监控页可以通过 Python 助手确认 restart_from，恢复同一个 workflowId，但不会经过钉钉 registerInbound/acquireForRestart。Java 常规定时对账更新运行记录和运行槽，并不重新激活钉钉绑定，因此新进度和完成消息不会发送，直到用户再从钉钉提问触发恢复。不是创建新 workflowId 的整项任务重试。
建议：为终态钉钉绑定提供有界低频状态检查，或由现有对账明确同步重新激活；不要无界轮询完整历史。尚未做真实三服务端到端复现。

### P2：消息收尾读取所有历史入站消息（代码确认，未压测）

位置：`services/role-task-config-center/src/main/java/com/codexflow/configcenter/integration/dingtalk/DingTalkStore.java:604`。
markInboundFinished 使用 inboundMessages.findAll() 后在 Java 筛选当前工作流 accepted 消息；每个回复都加载全系统消息历史（包含内容关联和临时回复地址字段），随保留历史增长持续加重数据库及内存成本。pollable 也先加载所有 terminal 绑定再过滤，终态越多轮询开销越高。
建议：用数据库 exists(workflowId,status) 查询和相应索引；将活动/等待助手条件放进 SQL。不要增加缓存或新的恢复后台来掩盖全表扫描。

## 系统复杂度判断

- 三服务的配置、运行、监控职责目前有明确用途；SQLite 的租约、幂等事件和任务互斥也有必要，不建议为了简化而合并服务或删除这些保证。
- 钉钉协调器 799 行、Store 883 行，新消息全为文本但仍注入未使用的 progressCard；workflowFinished、enqueueBindingText、supportsCard 等私有方法没有调用方。可以先清理这些死代码。历史卡片发送/回调和数据库迁移有兼容用途，不能整体删除。
- Java 的任务占用、钉钉 active 指针/绑定状态及 Python 权威状态需要反复对账。应逐步让通知只保存路由、游标和必要的投递状态，不再独立决定业务任务是否运行；但历史状态退役需有迁移设计，不能直接删列。
- Python store 3835 行、orchestrator 2189 行、gateway 2017 行，建议未来按控制动作/附件/事件等职责渐进拆分，并保留事务边界。文件长本身不是 bug，也不构成现在重写系统的理由。
- 图片格式校验自行实现 PNG/JPEG/WebP 结构解析，维护成本较高；本轮没有验证完整解码正确性，不把它当作已证明的安全解析器。
