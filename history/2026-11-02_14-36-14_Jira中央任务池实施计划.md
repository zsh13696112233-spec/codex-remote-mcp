## 已确认的产品决定

1. 定时任务采集到的工单持续排队，机器空闲后自动接着执行，不必等下一次定时触发。
2. 网页、钉钉手动启动也改成先查任务，最多启动一轮；无任务不创建空运行。
3. 用户确认同一 SOP 指定的账号别名在各监督机上对应同一真实 Jira 账号；实施时仍需核验身份，不能只凭别名认定相同。
4. 停用或修改定时规则后，停止旧来源尚未创建运行的派发，保留记录；已创建运行继续按原快照执行。等待新的有效触发重新采集确认。
5. 同一工单同时符合多个 SOP／任务定义时，先预约成功者执行，中央保证只被一轮占用；其他来源显示已被占用。
6. 监督机是全局池，不要求属于执行组。执行时仍使用任务对应组的执行机。

## 当前实现依据

当前顺序为：定时触发 → 查询空闲监督机与执行机容量 → 创建多轮运行 → 分配机器 → 监督机查询 Jira → 中央互斥领取 → 下发账号并执行。

- 配置中心 `WorkflowRunService.runScheduled` 使用 `/jira-capacity` 的机器容量创建批次，尚不知道实际工单数量；`DailyTaskScheduler` 约每 30 秒扫描，并保留执行前检查与资源等待机制。
- Python `jira_runtime.claim_next` 通过监督机既有 Jira CLI 查询候选，再由中央事务领取；候选页全部占用时排除编号继续查询。
- 中央已有 `workflow_jira_runs`、`jira_issue_claims`、`workflow_jira_deliveries`，分别承担运行台账、工单互斥和交付回执，尚无独立待分配池。
- 当前领取是平台内部登记，不自动修改 Jira 负责人或状态。旧执行已确认停止且后续查询仍满足条件时，终态工单可以再次领取。
- 本次未能成功读取本地运行库，因此没有核实用户描述的当天具体三轮运行；上述结论来自当前代码与文档，不代表已确认线上部署版本。

## 实施计划

### 1. 目标与执行流程

改为：**定时或手动触发 → 监督机查询 Jira → 工单进入中央任务池 → 按空闲容量预约工单 → 创建运行并执行。**

- 定时任务采集的待办持续排队，复用现有约 30 秒扫描，在资源空闲后继续派发。
- 手动触发最多启动一轮；无工单仅保存采集结果，不创建业务运行、不占用执行机。
- 第一版不增加独立采集周期，沿用现有定时规则；普通非 Jira 任务不变。

### 2. 采集与中央任务池

采集由平台固定代码执行，不启动模型监督会话。

- 从全局监督机池选择在线、检测通过、权限符合要求的空闲机器，使用 SOP 指定账号及完整 JQL 查询。
- 采集期间短暂独占该监督机，沿用机器互斥保护，不占用执行机；无空闲监督机时持久化请求并等待。
- 沿用既有 Jira CLI 和凭据读取方式。数据库仅保存规范化服务地址及非敏感账号身份，不保存密码、令牌或完整账号配置。
- 跨机器使用时核验账号身份；不匹配明确报错，不自动切换账号或混合不同账号任务。
- 完整查询候选工单，沿用排除已查询编号的分页方式与 1000 项上限。查询、分页异常或超限均标记采集失败，不以不完整结果判断无任务，不派发该批次。
- 相同任务定义的并发采集请求合并，避免手动与定时重复查询；合并采集不扩大手动触发仅一轮的执行授权。

中央 SQLite 增加工单池、采集批次及来源关联记录：

| 记录 | 核心内容 |
| --- | --- |
| 工单 | Jira 服务、工单编号、首次发现和最近核验时间 |
| 采集来源 | 任务定义、SOP 查询版本、账号身份、定时或手动来源 |
| 采集批次 | 稳定请求编号、采集机器、开始结束时间、结果及数量 |
| 预约关系 | 工单、来源、预约编号、关联运行及当前状态 |

同一工单按“Jira 服务＋编号”全局去重，允许关联多个来源。多个 SOP 同时匹配时，先预约成功者执行，其余显示已被占用。

### 3. 派发、恢复与兼容

Python 管工单与机器互斥，配置中心继续创建运行及不可变快照；不在 MySQL 和 SQLite 各维护一套独立领取锁。

- 配置中心根据待办和空闲容量申请预约；Python 在事务内预约具体工单，返回稳定预约编号，不能只返回数量再让运行竞争领取。
- 配置中心持久化启动请求，创建运行时冻结工单编号、预约编号、账号身份及 SOP 快照，沿用现有提交恢复机制。
- 网关接受运行时，在同一事务中将预约转成既有工单领取锁。不同来源、旧领取流程与人工重试均检查同一工单占用，防止新旧机制重复派发。
- 运行前只核验已绑定工单仍满足查询条件并下发账号，不重新搜索或替换工单。核验不通过结束该轮并记录原因，不执行业务步骤。
- 排队工单派发前由固定采集代码重新核验；人工转交或改状态后不再匹配的工单退出待办但保留记录。核验错误保留待核验状态，不能误判失效。
- 一次成功采集产生的待办资格只消费一次。运行结束后不立即将该资格放回队列；下一次有效采集再次返回该工单、旧执行确认停止后，才允许重新领取，保留返工语义。
- 预约、创建运行、提交均使用稳定请求编号实现幂等。超时或重启先核对原请求与运行，不能仅凭预约超时放回池；无法确认时保持待核实并阻止重复派发。
- 采集命令断连、无法确认停止时保留监督机占用，不因超时直接释放。
- 定时执行前检查保留：采集成功、有待办且具备执行容量后执行；通过结果在本批排队期间复用，不重复执行检查脚本。
- 停用／修改定时规则，停用／删除任务或 SOP，修改影响执行的配置时，撤销旧来源尚未创建运行的派发资格。已创建运行沿用冻结快照；旧待办记录保留，新的有效触发重新确认。
- 手动启动仅授权一轮，其他候选不因该手动操作自动继续执行。
- 历史运行、原快照重试保留兼容，重试限定原工单。账号下发、清理、停止核实、交付回执规则继续适用。

### 4. 接口与页面

- 新增网关的采集请求、采集状态、工单池查询与幂等预约接口；由配置中心 Java 客户端集中映射，浏览器仅访问所属 Java `/api`。
- 采集采用持久化异步请求，立即返回请求编号。网页显示“正在查找任务／等待采集机器”，轮询后展示运行入口、无任务或失败原因。
- 手动启动响应明确区分查找中、等待资源、无任务、已启动与失败；同步修改网页和钉钉调用方，不假定每次启动必有工作流编号。
- 钉钉沿用现有启动请求回复和通知机制，实际创建运行后才给出监控入口，不把采集请求当业务运行。
- “Jira 任务下发情况”增加“待分配工单”“采集记录”，保留运行历史及交付详情。
- 展示采集时间、来源任务／分组、待办数量、领取机器、关联运行、等待原因；区分没有工单、等待机器、被其他流程领取、采集失败和待核实。
- 不增加手动选机、优先级编辑、强制释放；不扩展 8090 监控中心控制职责。

### 5. 测试与验收

1. 两个工单、三组可用机器，只创建两轮；零工单不创建运行。
2. 五个工单、三组机器，剩余两条在资源释放后自动执行。
3. 同时定时触发、手动启动、跨 SOP 匹配及新旧领取机制并存，同一工单仅一轮占用。
4. 分页、账号不匹配、CLI 失败、网络中断明确报错，不误报无任务。
5. 排队后 Jira 条件变化不派发；业务启动前再次失效不执行业务步骤。
6. 预约成功响应丢失、任一服务重启、提交结果未知，不重复创建或领取。
7. 停用规则、修改 SOP、人工重试、历史运行与新队列并存，权限及占用规则一致。
8. 网页刷新恢复、空状态、失败保留、分页以及钉钉异步启动回复正确。
