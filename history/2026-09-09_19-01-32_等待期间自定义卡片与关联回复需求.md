## 用户最终需求（待实现）

仅在工作流处于步骤间等待时，等待相关通知和发给用户的正式回答统一改用自定义互动卡片，群和个人场景均需覆盖。

每张卡片应包含：

1. 当前等待状态、对应任务及必要的步骤信息。
2. 通知正文或助手对本次问题的实际回答内容。
3. @ 本次提问人；首次进入等待、尚无提问时，提醒任务发起人或既有通知接收人。群内应是真实 @ 提醒，不是仅显示姓名，不额外拆出一条提醒消息。
4. 两个按钮：**继续执行**、**回复**。
5. 回复操作及最终提交的文字、图片必须准确关联工作流；不能要求后端靠“最近任务”猜测。

“卡片有回复内容”的含义：回答正文展示在卡片中，卡片下面有上述两个操作按钮，不是把完整回答塞进按钮标签。

## 期望的完整交互

1. 策划步骤完成，开发尚未开始，发送等待卡片，展示两分钟无人操作自动继续规则，提供“继续执行／回复”。
2. 用户点“回复”，提出某张图片有问题。回复过程应先保持当前等待，取消自动继续，再处理提问；用户输入期间不能被倒计时抢先放行。
3. 助手用卡片回答，例如解释为何采用该设计；该回答卡片 @ 提问人，并继续提供“继续执行／回复”。
4. 用户认可回答，点“继续执行”直接放行当前等待，不再先发“已保持等待，请确认继续”。
5. 用户不认可回答，点“回复”继续追问，可持续多轮沟通并发送图片；任务始终保持等待，直到明确继续。
6. 等待结束后，本轮所有相关卡片的继续按钮失效，后端也必须拒绝过期操作；返工后的新等待不能被旧卡片放行。

用户明确反对删去“回复”按钮：它承担从当前回答继续沟通的入口，不能只保留“继续执行”。也不能把“回复”做成仅暂停任务、没有实际提问入口的假按钮。

## 范围与沿用规则

- 等待期间的正式回复使用卡片；执行中或已结束后的普通对话不因本需求全部卡片化。
- 等待状态通知可以更新同一张状态卡片；多轮回答应保留回答历史，不要用更新把前面的回答覆盖掉。具体卡片组织方式需在实现前整理清楚。
- 两分钟自动继续、提问/图片后保持等待、旧引用及重复消息保护、执行中禁止控制、终态返工保持原规则。
- 卡片发送成功后的计时、回执重试、不重复发送、失效通知过滤需保持与现有等待通知语义一致。
- 不新增停止、跳过、返工按钮，不增加等待自动释放名额、动态并发或新的恢复机制。
- 隐藏等待期间助手思考摘要曾由助手提出作为减少杂乱消息的建议，用户未单独明确确认该调整；不能把它误记为已实现或已决定。

## 已核对的事实与能力边界

### 当前消息并非自定义卡片

- 截图中的原生“收到／回复”来自钉钉文字消息的客户端展示，当前项目发送的是文本正文及 @ 参数，并没有配置这两个原生按钮。
- 当前文本接口不能把原生“收到”改名或绑定为“继续执行”。用户选择了用自定义卡片实现所需操作。
- 个人主动通知使用 `sendPersonText`，和群会话回复的样式不同；不能仅切换一个文本参数就保证个人也出现相同原生按钮。

### 可以确认的卡片能力

- 自定义卡片支持按钮文案、按钮回调、内容更新和状态展示。
- “继续执行”可以携带工作流与等待标识，复用后端确认接口。
- 卡片投递支持 @ 参数，官方 SDK 的创建并投递模型包含 `atUserIds`。具体用户标识类型、群及个人展示需随最终使用的 API 校验。
- 卡片表单可以提供文字输入和提交回调；这不等于原生图文回复输入框。

### 关键未确认项：回复入口

**尚未找到明确的官方接口，证明自定义“回复”按钮可以直接打开钉钉原生的带引用输入框，并同时发送文字、图片。没有做真实卡片模板或客户端验证，不能承诺已支持。**

后续需要先验证：

- 卡片按钮是否支持原生回复入口；PC 和手机、群和个人是否一致。
- 使用钉钉原生引用卡片时，入站回调是否携带可稳定匹配的消息/卡片标识。
- 图片和文字能否作为一次关联输入到达；截图、附件、引用正文是否被解析成正确字段。
- 若无法原生实现，需要提出能满足“继续沟通且准确定位”的替代入口，由用户确认交互变化。卡片内文字表单是可行方向，但尚未解决图文一体体验，用户未接受以此替代完整要求。
- 不采用“点击回复后把该用户下一条任意消息归到该任务”的隐式猜测作为默认方案。同群多任务、连续点击不同卡片、超时和取消会带来误关联，且用户要求功能简单。

没有按钮也可以用带工作流编号的消息定位，但这不是用户要求的最终一键回复体验，不能用这个退路冒充需求已完成。

## 当前代码入口（需重新核对后使用）

- `services/role-task-config-center/src/main/java/com/codexflow/configcenter/integration/dingtalk/OfficialDingTalkTransport.java`：
  - `sendCard` 有卡片发送基础，当前投递场域为 `dtv1.card//IM_GROUP.`，不能据此声称已支持个人卡片。
  - 当前卡片使用模板 ID 与 `callbackType: STREAM`。
  - `sendReply`、`sendPersonText` 是现有文字链路。
  - 卡片回调解析、消息引用和图文解析都在此模块附近。
- `DingTalkBotCoordinator.java`：等待事件消费、正式回答、Outbox 投递、`handleAction` 的 `advance_hold/advance_confirm` 处理。
- `DingTalkStore.java`、Outbox 和 Binding：当前等待邀请、保持通知、回答路由、具体等待关联、发送回执、引用匹配。现有单个进度卡片实例字段不应未经审查就用于一轮等待的多张回答卡片。
- `services/python-workflow/src/workflow_gateway.py` 和 `workflow_store.py`：中央权威等待、确认、保持、入站消息幂等；后端必须再次检查当前等待，不能仅依赖按钮禁用。
- 配置中心已有 `cardTemplateId` 和历史卡片代码，但并未完成本次自定义卡片产品流程。需要创建并发布模板、明确变量和按钮回传参数、核对权限与 Stream 回调，不能只填模板 ID 就宣布完成。
- 仍遵守 8091 控制、8080 运行边界、8090 监控代理边界，不因卡片需求新增监控中心直接控制能力。
