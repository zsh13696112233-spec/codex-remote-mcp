## 审查结论：12 项待处理问题

下列问题均为**仅审查发现，尚未修复**。P1 建议优先处理；P2 为功能兼容或规模增长后的性能问题。证据分别标明隔离复现、静态分析或尚未真实环境验证，不能把它们统一视为生产复现。

### 1. P1：任务助手没有显式隔离业务工具

- 位置：`services/python-workflow/src/workflow_gateway.py` 的 `_run_assistant_model_turn`（基线约 967 行）；`codex_orchestrator_mcp.py` 的 `_run_job`（约 1241 行）。
- 助手在主监督执行服务上启动独立会话，仅设置只读、禁止审批和结构化输出，没有显式禁用 MCP、应用和插件，也没有核验有效工具清单。
- 主监督按文档配置编排 MCP 时，助手可能继承业务工具；提示词要求不执行业务，不构成确定性的工具权限限制。`cancel_node` 等工具自身不经过聊天控制的二次确认链路。
- 影响：模型误用或受输入影响时，存在绕过助手控制边界的风险。
- 优化：为任务助手单独构造工具隔离配置，对新建与恢复会话均核验；仅允许通过结构化 `tool_request` 进入平台确定性查询/咨询逻辑。
- 证据：静态调用链分析；没有连接真实执行服务验证助手实际获得的工具，也没有进行模型诱导测试。

### 2. P1：SVG 附件存在同源脚本执行风险

- 位置：`services/python-workflow/src/workflow_gateway.py` 的 `get_workflow_artifact`；`services/workflow-console/src/main/java/com/codexflow/console/web/WorkflowController.java` 的 `artifact`（约 80 行）；监控前端 `appendStepArtifacts`。
- Python 和 Java 均把所有 `image/*` 作为 `inline` 返回，包含 `image/svg+xml`；前端“打开原图”在新标签打开同源附件 URL。
- 影响：带脚本的 SVG 在作为文档打开时具有同源脚本执行风险，可以访问监控中心 API。`nosniff` 和 `noopener` 不等同于 SVG 文档脚本隔离。
- 优化：内联展示采用安全图片类型白名单；SVG 强制下载，或使用独立隔离域/受限展示策略；两端响应及前端分类同步处理。
- 证据：隔离调用实际 Python 下载处理函数，确认 SVG 返回 `200`、`image/svg+xml` 和 `inline`；未做真实浏览器攻击验证。

### 3. P1：Sidecar 失联取消没有传递到底层监督任务

- 位置：`services/python-workflow/src/workflow_gateway.py` 的 `_sidecar_watchdog_loop`（约 412 行）、`_run_supervisor` 取消分支（约 616 行）；`codex_orchestrator_mcp.py` 的 `_run_job` 执行机串行锁。
- 心跳超时处理只取消网关持有的外层监督协程；其取消分支没有同步停止由 Orchestrator 独立创建的任务。
- 影响：底层任务可能继续运行并持有执行机串行锁。数据库租约已经释放、Sidecar 恢复后，新任务仍可能等待旧任务结束或超时。
- 优化：统一取消生命周期，处理底层任务中断、连接清理和锁释放；必须区分本地协程结束与远程执行确已停止，并防止旧回调影响后续运行。
- 证据：从源码提取实际 `_run_supervisor`，使用隔离存储/调度替身复现“外层已取消，独立底层任务仍运行”；未验证真实 app-server 中断与失联恢复。

### 4. P1：已完成任务缓存保留附件原始字节

- 位置：`services/python-workflow/src/codex_orchestrator_mcp.py` 的 `Job`、`_prune_completed_jobs`、`cleanup_managed_artifacts`（约 1182 行）、`_stage_artifacts_sync` 和 `_capture_artifacts_sync`。
- Orchestrator 默认保留 1000 个任务。任务完成及托管目录清理后，`staged_artifacts`、`captured_files`、`input_images` 中的正文仍被任务对象引用。
- 累计文件交接会让多个步骤分别保留前序文件副本，任务数量上限不能有效限制字节总量。
- 影响：文件流水线及图文咨询长期运行时，内存可能达到数 GB；尚未测量实际部署的 RSS 或触发 OOM。
- 优化：输入落盘、输出可靠落库且不再需要重试后释放正文，保留元数据；增加字节总量/过期策略。释放时必须保证重复状态查询和失败重试的幂等性，不能只清空后破坏持久化流程。
- 证据：隔离执行实际目录清理和缓存淘汰方法，临时目录已删除、完成任务仍在缓存，构造的输入/输出/图片共 3 MiB 字节数据仍被保留。

### 5. P2：中文文件名导致附件下载失败

- 位置：`services/python-workflow/src/workflow_gateway.py` 的 `get_workflow_artifact`（约 1468 行）；Java 监控客户端的文件名解析也需同步检查。
- 文件名原文直接放进 `Content-Disposition`。Starlette 对响应头进行 Latin-1 编码时，中文触发 `UnicodeEncodeError`，随后被宽泛的 `ValueError` 分支映射为 404。
- 影响：附件已保存但中文文件名无法下载，同时对用户返回内部编码错误。
- 优化：使用标准 UTF-8 `filename*` 和兼容回退文件名；Java 支持解析该格式；区分对象不存在与响应构造失败。
- 证据：隔离调用实际下载处理函数，`report.txt` 返回 200，`分析报告.txt` 返回 404 和 `UnicodeEncodeError`；只替换存储返回值，没有导入整个网关或访问实际业务附件。

### 6. P2：Python 3.10 兼容声明与实现不符

- 位置：`services/python-workflow/pyproject.toml` 的 `requires-python = ">=3.10"`；`workflow_store.py`、`codex_orchestrator_mcp.py`、`workflow_sidecar.py` 的 `from datetime import UTC`。
- `datetime.UTC` 从 Python 3.11 才提供，因此 Python 3.10 会在导入核心模块时失败。
- 优化：按当前仓库约束保持 3.10 兼容，使用 `timezone.utc`；同时检查 `asyncio.TimeoutError` 与内建 `TimeoutError` 的版本差异，不要只修导入。
- 证据：静态兼容性检查；本机已有虚拟环境为 Python 3.11.15，没有运行 3.10 验证。

### 7. P2：Python 打包清单遗漏必要模块

- 位置：`services/python-workflow/pyproject.toml` 的 `[tool.setuptools].py-modules`（约 24 行）。
- 缺少 10 个本地模块：`agent_registry`、`mcp_deployment`、`mcp_diagnostics`、`mcp_installation`、`mcp_packages`、`mcp_routes`、`mcp_store`、`mcp_terminal`、`workflow_consultation`、`workflow_service_config`。
- 影响：直接从源码启动或 editable 环境可能掩盖问题；构建 wheel 后在干净环境安装，会遗漏入口依赖的内部模块。
- 优化：补齐打包清单，验证 wheel 内容及隔离安装后的入口导入/启动。
- 证据：比较源码模块、打包清单和 AST 导入关系；本机虚拟环境缺少 setuptools，未构建 wheel，也未安装工具。

### 8. P2：咨询记录读取全量历史后才过滤

- 位置：`services/python-workflow/src/workflow_consultation.py` 的 `records`（约 223 行）。
- 本地回退先查询指定步骤的全部事件并逐条解压、解析，再按执行版本和事件类型过滤，最后应用字符上限。输出限制不限制前面的数据库读取和内存成本。
- 远端路径还会 `thread/read(includeTurns=True)` 读取全部轮次，再选目标轮次；真实协议是否有可用的更窄查询需另行核验。
- 优化：事件类型、执行版本尽量在数据库侧筛选，分批读取并提前施加容量限制；保留分页快照固定来源、顺序和版本的语义。
- 证据：临时 SQLite 中构造 10000 条每条约 2 KiB 的无关历史增量事件，执行实际 `records(remote=False)`，全部 10000 条被解压，最终返回 1 条记录。`tracemalloc` 记录的 Python 峰值分配约 33.4 MiB，带追踪执行约 0.12 秒。该数字不是进程 RSS 或生产吞吐结果。

### 9. P2：MCP 队列缺少领取索引且持写事务扫描

- 位置：`services/python-workflow/src/mcp_store.py` 的 `claim`（约 191 行）；`mcp_deployment.py` 的三个后台 worker。
- 领取查询按 `state='queued' ORDER BY created_at,id`，但表只有主键及机器占用的部分唯一索引，没有该队列索引。查询使用 `fetchall`，位于 `BEGIN IMMEDIATE` 内；空队列下每个 worker 约每秒重复检查。
- 影响：即使没有待办也随完整历史增长扫描，增加 CPU、数据库读取及共享 SQLite 写锁竞争。
- 优化：增加兼容的队列索引，限制每轮候选数量并缩短事务；避免被占用机器的候选使其他机器长期饥饿。
- 证据：使用源码建表 SQL 构造内存 SQLite，放入 100000 条已完成记录、零待办。查询计划为 `SCAN mcp_tasks` 和临时排序，约 300000 条 SQLite 虚拟机指令；临时添加 `(state,created_at,id)` 索引后变为索引搜索。本机单次约 2.23 ms → 0.02 ms，仅说明合成数据下的查询变化，不代表线上收益倍数。索引没有写入项目或业务数据库。

### 10. P2：MCP 安装列表每 3 秒拉取完整历史

- 位置：`services/python-workflow/src/mcp_store.py` 的 `tasks`（约 139 行）、`mcp_routes.py` 的 inventory 路由；`services/role-task-config-center/src/main/resources/static/mcps.js` 的 3000 ms 轮询。
- inventory 读取并返回全部逐机历史任务，无分页或增量版本，前端再挑选每个包最近的记录。没有安装活动时也持续拉取；查询还用 `t.*` 读取响应不需要的内部快照字段。
- 影响：历史越多，SQLite 读取、Java/Python JSON 处理、网络和浏览器处理成本越高，多页面同时打开进一步放大。
- 优化：服务端直接返回最新安装汇总，读取必要列；历史独立分页；活动状态正常刷新，终态/空闲降低频率，考虑版本号复用。
- 证据：静态接口与前端调用链核对，未做多客户端压测。

### 11. P2：Skill 汇总与历史存在逐条查询和反复开连接

- 位置：`services/python-workflow/src/skill_store.py` 的 `batches`、`inventory`、`batch`、`package`（约 161 行起）。
- inventory 每行重新查询包和分组，失败任务追加可重试校验；batches 先取最多 100 个编号，再逐个查询批次和包。
- 读取 100 个批次，基础路径约打开 201 次 SQLite 连接；失败任务校验会继续增加。机器/历史页面每 3 秒轮询时会反复付出该成本。
- 优化：批量加载任务、包与分组；同一次读取复用连接，对重复包去重查询。保留冲突包不覆盖原安装展示、分组归属和重试资格语义。
- 证据：静态查询和连接次数分析，未测实际生产列表延迟。

### 12. P2：运行对账串行查询完整状态

- 位置：`services/role-task-config-center/src/main/java/com/codexflow/configcenter/application/WorkflowRunService.java` 的 `reconcileActiveRuns`（约 142 行）；`DailyTaskScheduler` 的单线程 reconciliation；`client/GatewayClient.java` 的 30 秒请求超时。
- 对账按全部活动占用逐个请求完整工作流状态，单个慢响应阻塞后续项。若 20 个请求各等满 30 秒，单轮理论上可耗时约 10 分钟。
- 影响：终态运行槽释放、提交不确定状态的恢复延迟；此处不是定时扫描直接阻塞，但会影响任务占用及时释放。
- 优化：优先复用已有 `/workflow-statuses` 批量轻量状态查询；详情和缺失运行恢复按需处理，保留 404 与未知结果的保守语义，限制单轮耗时。
- 证据：静态调用链及超时预算分析，10 分钟为条件性估算，没有等待真实超时复现。

## 优化顺序与修改量评估

建议分三批实施，不自动把审查授权理解为修复、部署或提交授权：

1. 安全与稳定性：工具隔离、SVG、底层任务取消、附件内存释放。
2. 功能与部署可靠性：中文下载、Python 3.10 兼容、打包清单，并修正过期测试断言。
3. 数据增长后的性能：咨询筛选/分页、队列索引、安装汇总和轮询、Skill 批量查询、运行批量对账。

初步评估为中等总体修改量，不需要据此重构整个项目：

- 中文下载、兼容导入、打包清单、队列索引：小改动。
- SVG、防止工具越权、批量查询和轮询：需跨边界核对，范围因具体方案而异。
- 任务取消、附件释放、咨询分页：验证工作较多，须覆盖异步生命周期、恢复、幂等、失败重试和旧数据。
- 先前向用户给出的全部修复粗估是 15–25 个生产文件，另加测试和文档；这是未实施前的范围估算，不是承诺或已完成工作量。
