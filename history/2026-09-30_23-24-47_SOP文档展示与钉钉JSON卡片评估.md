### AI 卡片可行性结论

技术上可行，现有互动卡片链路可以作为基础；但不能只更换模板 ID 就认定迁移完成。这里评估的是官方已有的模板式 AI 卡片及其流式更新能力，不将其与后文尚未核实完整接入协议的 JSON 构建卡片混为一谈。

本次在线核对的官方资料：

- [钉钉官方卡片示例](https://github.com/open-dingtalk/dingtalk-card-examples)包含 AI 卡片流式更新示例，并说明通过 Stream 接收卡片交互回调。
- [官方 Python SDK 的 CardReplier / AICardReplier](https://github.com/open-dingtalk/dingtalk-stream-sdk-python/blob/main/dingtalk_stream/card_replier.py)显示：AI 卡片沿用模板 ID 创建，支持群聊及单聊投放；普通更新和流式更新分别调用卡片实例接口与 `/v1.0/card/streaming`。这用于核实平台能力，不表示本项目应改用 Python SDK。
- [AI 卡片流式更新接口](https://open.dingtalk.com/document/orgapp/api-streamingupdate)本次网页正文未能提取；完整容量、限流、重试和终结后更新约束仍须核实，不能根据 SDK 示例推定平台保证。

结合当前代码，建议与限制如下：

1. 配置中心已有创建、投递、更新、固定卡片标识、投递回执及 Stream 按钮回调链路，可复用其业务边界。AI 卡片的布局、变量和完成状态需要适配；当前代码尚未接入流式更新接口。
2. 建议卡片保留「总结」「文档」「继续执行」三个区域；没有文档时不展示文档区域。自定义模板是否支持所选布局、正文长度和按钮组合需验证，不能承诺默认 AI 模板已包含这些能力。
3. AI 卡片只负责呈现，不能自动读取执行机文件。文档明确上报、权限和路径校验、正文快照、多份文档及讨论同步仍需单独实现；切换卡片不会解决当前附件为空的问题。
4. 首版建议在步骤完成后展示已保存的总结和文档，不将逐字流式输出作为文档展示的前置要求。如果后续启用实时输出，再补增量来源、更新节流、版本顺序、失败重试与最终内容收敛；不能把重复播放完整结果当作真实生成进度。
5. 保留讨论处理中禁用按钮、旧等待拒绝放行、会话与操作人校验。卡片内容生成完成与工作流等待结束必须分别处理，不能用 AI 卡片的完成状态直接放行下一步骤。
6. 当前每条等待正式回答创建独立卡片，正文快照独立保留；建议沿用该边界，避免反复重开已终结的流式字段。文档版本及按钮状态能否在卡片完成后继续更新，需要真实验证。
7. 群聊和单聊的投递、引用回复关联、真实 @、按钮回调、长文档显示及网络结果不明确时重试，均需用目标应用和客户端验收。本次仅核对代码、现有测试和官方资料，尚未完成这些验证。

## 钉钉 JSON 卡片评估

用户明确偏好代码构建 JSON 卡片，认为外部模板方式维护臃肿。

参考入口：[JSON 构建卡片](https://open.dingtalk.com/document/development/json-build-card)。本次网页读取和浏览器连接均失败，未在线核实该页完整内容；用户随后粘贴了“消息结构与生命周期”协议文本，以下结论以该文本为依据。另查到[钉钉官方卡片示例](https://github.com/open-dingtalk/dingtalk-card-examples)，只能支撑既有模板、创建、更新及回调能力，不能替代新版接入文档。

用户提供的协议说明：

- 四种消息为 `createSurface`、`updateComponents`、`updateDataModel`、`deleteSurface`，每条只包含一种载荷。
- 消息包络 `version` 为 `v1.0`，投递 `protocolVersion` 为 `1.0`，产品能力集 `aicardVersion` 为 `V0.8`；三者含义不同。
- 新卡显式创建画布并填写钉钉 `catalogId`；宿主已创建时不要再次创建。同卡所有消息使用同一 `surfaceId`。
- 组件树根 ID 为 `root`，组件 ID 和引用必须有效、稳定，动态绑定使用前初始化正确类型的数据。
- 仅字段契约支持时可用动态绑定；数据变化更新数据模型，结构或普通字段变化更新组件。
- 钉钉协议是 A2UI 的子集加扩展，不可直接替换成通用 A2UI 实现。
- `catalogId` 是运行时标识，不是下载地址；钉钉当前不执行以 `null` 删除数据字段的语义。

建议由配置中心 Java 固定构建组件 JSON，执行步骤只提供总结和文档数据，不让业务执行者自由生成按钮和整张卡片。

卡片建议分总结、文档、操作区域；无文档不生成文档区域。保留现有等待、讨论处理中禁用、过期按钮拒绝及按钮放行规则。持久化卡片与画布对应关系，避免发送重试重复创建，控制更新顺序，防止旧内容覆盖新版本。具体折叠、页签、Markdown 文档组件尚未核实，不作为已支持功能。

## 旧版清理的讨论结论

新版完整可用后可以删除旧实现，不必长期维护两套：

1. 切换期新卡使用新协议，保留旧卡更新和回调，等待旧卡关联的活动流程结束。
2. 验证新版发送、更新、引用回复、按钮及失败重试，并确认没有活动流程依赖旧卡后，删除旧模板构建、发送、更新、专用配置和相应测试文档。
3. 历史记录不删除，已应用 Flyway 迁移不修改；废弃字段如需删除，通过新迁移处理。
4. 可保留很小的过期回调处理提示旧卡失效，防止旧按钮误操作当前流程，无需因此保留整套旧版。
