## 已确认的产品决定

1. 只在领取中心工单池及启动通知增加人员展示，等待、遇阻、结束等其他卡片保持现状。
2. 开发人沿用 `Public.Jira.Fields.Developer` 对应的实际 Jira 字段；支持多人。
3. “负责人”明确指 Jira 当前经办人 `assignee`，不是阻断转交时使用的配置项 Manager。
4. 人员信息读取失败时允许继续启动，页面和通知明确标注失败；不把人员展示变成新的业务派发条件。
5. 人员展示使用最近采集值，启动通知使用本轮冻结的采集值，不宣称实时同步。
6. 不修改 Jira 人员、领取条件或派发规则，不新增人员管理、自动 @ 或通知对象。

## 当前实现依据

- Python `jira_runtime.search_page` 目前只返回工单编号与标题，`jira_pool` 将其存入中央 SQLite，并负责工单合并展示、预约及绑定。
- 领取条件包含 `assignee = currentUser()`，负责人可能显示自动化账号，不一定是实际开发人员。
- 业务步骤已有 `jiraDeveloper` 结果和运行时 Jira 上下文，但它们依赖步骤执行后回传，不能覆盖尚未执行的候选工单。
- 配置中心将预约冻结在运行的 `jiraReservation` 中；启动请求查询经 `jiraIssue` 提供编号和标题。
- `DingTalkExecutionNotice.jiraStart` 已是启动 Jira 信息的公共拼接入口。钉钉异步启动和定时启动使用现有卡片入口，已开启通知的网页启动沿用现有文字通知。
- 网关对预约字段有严格校验，新增人员字段必须同步调整契约，不能只改前端或 Java 通知。

## 实施计划

### 1. 采集与保存

- 首先只读核实部署环境中的开发人字段映射及 Jira CLI 返回结构，不猜测自定义字段编号，不输出凭据或完整业务记录。
- 复用监督机现有 CLI：搜索结果包含人员字段时直接解析；未返回时，通过只读工单详情查询补充。人员补充查询与工单搜索的完整性判断分开。
- 保存两类人员的实际账号标识、显示名、读取状态和采集时间；开发人支持多人。
- 人员为空、未采集和读取失败分别记录。已确认的人员查询失败不阻止派发；工单搜索失败、身份不一致及远端停止状态不明仍遵守现有保护。
- 中央 SQLite 工单池增加可选人员 JSON 字段，通过增量迁移兼容旧库。共享采集结果时同时复制人员信息。

### 2. 接口与运行快照

- `/jira-pool` 返回人员信息；同一工单合并展示时，使用最近一次采集的人员及状态，不能把旧姓名当成此次成功读取结果。
- `/jira-reservations` 的预约结果增加可选人员信息，随 `jiraReservation` 冻结到本轮运行；同步扩展网关输入校验和预约一致性校验。
- `/api/jira-requests/{id}` 的 `jiraIssue` 增加用于展示的人员字段，按白名单输出，不透传凭据、服务地址或完整预约对象。
- 重复预约、提交恢复和通知重发使用同一份冻结信息。后续采集只更新领取中心，不改写已有运行及启动通知。
- 复用现有 MySQL JSON 快照存储，不新增人员表；不把采集信息写入业务步骤的 `jiraDeveloper` 结果，避免改变现有通知逻辑。
- 浏览器仍只访问配置中心 `/api`，不直连 Python 或数据库；不扩展监控中心职责。

### 3. 页面与启动通知

- 工单池增加“开发人 / 负责人”一列，分两行展示，并提供人员采集时间。现有分页、筛选、后台刷新及执行详情保持可用。
- 复用现有启动通知公共拼接方法和模板，覆盖钉钉启动、定时启动及已开启通知的网页启动；网页原有文字通知保持文字形式。
- 示例：

```text
Jira：TEST-123
工单标题：修复订单列表
开发人：张三、李四
负责人：自动化处理账号
```

- 空字段显示“未设置”，读取失败显示“读取失败”，旧记录缺失显示“未采集”。人员显示名统一处理 HTML／Markdown 转义。
- “正在查找工单”的受理消息不展示人员；确定工单、提交成功后的启动通知再展示。保留现有消息去重及发送顺序。
- 历史数据不批量回填，已发卡片不补发；按原快照重试不猜测缺失人员。
