## 已完成的主要功能与修复

### 已提交的半自动等待与控制限制

- 半自动成功步骤之间等待 120 秒；明确继续立即放行，无回复自动继续。最后一步不新增等待。
- 等待时提问、图片或暂停请求先保持等待、取消自动继续，之后需要明确继续。
- 全自动、半自动的业务步骤执行期间均拒绝停止、跳过和重跑，不预约、不延迟执行，不因被拒绝的控制中断业务步骤。终态重试、返工保持原行为。
- 钉钉通知绑定具体等待，首次有效发送回执将截止时间调整为发送成功后 120 秒；重复、迟到回执不延长或重启等待。通知失败与未启用通知按创建时间兜底。
- Python 状态与事务、SQLite 兼容升级、本机和远程等待读取、Java 通知、两个页面及 README 同步调整。Java V23 保存等待通知关联与发送时间。

- 此恢复说明不能用于已成功应用 V23 的正式数据库；不得删除其他迁移记录或随意改动已应用迁移。正式支持基准仍为 MySQL 8。

### 未提交：等待通知样式和执行消息

- 钉钉启动且有会话回复地址时，等待邀请改用与助手回答相同的文字回复链路，群内 @ 发起人；无会话地址仍使用主动文本。
- 等待邀请改成会话回复后仍保留 Outbox 重试；发送成功但回执失败时只重试回执，不再发正文。普通助手回复仍不补发。
- 等待期间过滤主监督文字、可读摘要和工具进度，用户提问的助手回答保持正常。
- 消费事件和投递前均检查等待状态；Outbox 保存主监督事件来源及时间，通过当前节点的依赖、完成时间、启动时间过滤延迟消息。
- 不再把主监督 `dispatch_node` 请求的开始显示为步骤启动，实际步骤开始由 `node.started` 提示。
- 保持等待正文和独立 @ 提醒合并成一条完整回复，不再追加“任务状态已更新，请查看上方消息”。保持也可能由暂停触发，因此不声称助手已开始处理问题。

### 未提交：返工后等待引用歧义

- 同一工作流返工后可能生成相同正文的等待邀请。会话回复缺少可匹配消息编号时，原正文匹配遇到多条会拒绝定位。
- 等待邀请新增“第 N 次等待确认”，在工作流行锁内按已持久化的不同等待通知计数，重试复用原正文，不新增数据库字段。
- 测试覆盖两轮相同业务正文、无消息编号的引用定位、重复事件，以及旧引用仍指向旧等待。
- 真实截图的原始回调未取得，因此当时的精确失败原因仍有证据限制；上述正文歧义缺陷已通过代码及回归测试确认并修复。
- 已发送的历史重复正文无法补改，仍拒绝歧义匹配；可用工作流编号加“确认继续”定位当前等待。

### 未提交：确认继续不再先保持

- 实际事件曾出现明确继续后先 held，约 10 秒后再 confirmed，导致先收到“请确认继续”再收到“已确认”。原因是确认入口复用了会暂停主监督的普通输入观察接口。
- `POST /workflows/{workflowId}/input-observations` 新增可选布尔 `hold`，默认 true；false 只持久记录首次对应等待与控制许可，不改变等待、不暂停主监督。
- Java 明确继续传 `hold: false`，随后调用原确认接口；无当前等待分支也使用该参数，避免检查期间出现新等待时误保持。
- 重复消息仍绑定首次等待，旧引用校验保留；图片和普通提问仍走先保持逻辑。此次调整针对钉钉明确继续链路，未改网页普通聊天文本的识别流程。
- 没有新增调度恢复机制、没有改变重启清理策略。
