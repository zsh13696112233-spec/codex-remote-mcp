# SOP 分组调度、Jira 统一领取与启动排障交接

## 本次目的与环境

- 将工作目录从 SOP 移到执行机登记；SOP 绑定执行分组，自动分配空闲监督机和执行机。
- 实现监督机通过已有 Jira CLI 查询工单、中央防重复领取、向执行机下发同一账号，以及按组查看领取、分配和交付结果。
- 沿用现有定时任务触发，处理机器忙碌时的资源等待；随后排查网关后台报错和配置中心一直显示“正在检查网关”的问题。
- 操作系统：macOS。文件名使用北京时间。
- 当前分支：`codex/test-environment`；基线提交：`11dd24a`。
- 用户明确授权本次写入 history。业务改造、排障修复和本总结均尚未提交、未推送；没有部署到正式环境。
- 本机测试服务使用 `127.0.0.1:18080`（网关）、`18090`（监控中心）、`18091`（配置中心），与正式端口隔离。环境操作参见 [测试环境说明](../docs/TEST_ENVIRONMENT.zh-CN.md)。

## 必须保持的业务约束

1. **一轮 SOP 运行始终使用同一台执行机、同一个登记工作目录。** 不论有多少步骤，都不按步骤换机器或目录；执行顺序由 `dependsOn` 决定，当前只接受串行链。沿用文字总结和共用目录中的业务文件协作，不重新引入文件交接模式。
2. **一台执行机同时只能接一轮运行。** 步骤间等待、人工确认、讨论、遇阻和当前步骤重做均保持整项占用。安装及定时检查脚本也不能绕过互斥。
3. **纯监督机使用全局池。** 新建、编辑纯监督机时页面不要求执行分组并提交空分组；旧记录可能保留历史分组，但不限制监督调度。兼任执行机的机器仍需绑定执行组，其监督职责可跨组。
4. 当前实现一轮同时占用一台监督机和一台不同的执行机，监督机也保持单轮占用。A 组有三台执行机不代表必然能并行三轮，还需三台合适的空闲监督机；不是让一个 SOP 的不同步骤分散到三台机器。
5. 工作流终态、租约到期、网关重启或中断请求成功，均不能单独证明远端执行已停止。未确认停止时继续保留占用，不给该机器派发新任务。
6. 启用 Jira 后，一轮运行只处理一个工单；具体读取、修改、评论和交付由执行机做。监督机负责查询与编排，不代替业务步骤。
7. 中央“领取”是平台的互斥登记，不等于已经更改 Jira 的负责人或状态；“流程完成”也不等于已经提交代码。提交必须有实际确认的提交号或交付链接。
8. 工作流提交快照保持不可变；实际机器分配另行持久化。按原快照重试不套用最新 SOP 配置。
9. 全局调度与 Jira 台账属于配置中心；监控中心继续只展示指定的单个工作流。浏览器只访问所属 Java 服务，Java 通过 Python 网关访问运行时。

## 已完成的实现

### 分组调度、目录和机器占用

- 新 SOP 使用分组调度，不再手选监督机、执行机或配置 SOP 工作目录；机器登记新增工作目录字段。历史固定机器运行保留兼容。
- 网关从全局监督机池和目标组执行机中选取符合在线、检测、权限、模型等条件的空闲组合；同一 SQLite 写事务内同时领取两台机器，未获得组合则排队。
- 实际分配保存在 `workflow_allocations`，整项占用保存在 `workflow_machine_claims`，派发和停止核对使用持久化执行保护记录。未确认停止时展示“执行状态待核实”。
- 机器占用期间限制连接、目录、分组等编辑，备注仍可修改。模型能力检查和远端停止核对在后台执行，避免阻塞心跳续租。
- 远程 Sidecar 通过认证与有效租约访问中央状态；无活动租约时只能读取自身配置，有租约时仅访问本轮分配的机器。
- 配置中心机器页展示全局监督机与按组执行机；运行记录增加“机器分配”，展示实际机器、目录、等待原因及占用情况。
- 主要代码：`services/python-workflow/src/workflow_resources.py`、`workflow_allocation.py`、`workflow_store.py`、`workflow_gateway.py`、`agent_registry.py`，以及配置中心 SOP、运行服务和 `static/machines.js`、`allocation.js`。

### Jira 领取、账号下发和结果台账

- SOP 增加 Jira 开关、JQL 和账号别名，冻结到运行快照。旧 SOP 不会自动启用 Jira；部署后需明确配置。
- 监督机在派发业务步骤前调用 `jira_claim_next`。固定运行时代码在监督机上使用已有 `jira_cli`，不需要 CLI 源码，平台不直接连接 Jira HTTP API。
- 账号来自监督机固定配置路径 `C:\Users\admin\.jira_cli\config.json`；账号别名留空仅适用于文件中恰好一个账号。真实账号、令牌和配置内容不写入本总结。
- 中央按规范化 Jira 服务地址与工单编号进行跨组去重。候选全部被占用时排除已查询编号继续查询；真正无候选时登记“无可领取工单”并结束，不执行业务步骤。CLI、网络或格式错误不能当作无任务。
- 运行专属账号与 PowerShell 入口通过内部文件通道写到执行机，回读确认后才允许派发。执行步骤通过该入口使用相同账号读取和修改固定工单，不覆盖执行机全局 Jira 配置。
- 用户明确允许内网传输账号及 token。实际凭据不进入中央数据库、提交快照、模型提示词或平台事件；入口保留账号只读限制，拒绝覆盖认证、重选工单和修改 CLI 配置。
- 终态且远端停止确认后清理运行专属账号文件。失败保留待清理状态；尚未清理的机器不能删除或改变连接地址，允许修复连接凭据后继续清理。
- 已完成工单不自动重复领取；失败或取消后须旧执行已确认停止、且再次查询仍符合条件才可重领。按原快照重试通过 `jiraRetryOf` 限定原工单，不自动换单。
- 新增“Jira 领取与结果”页面，可按组或查看全部，支持分页和定时刷新，显示领取、分配、等待、失败、中断和历次交付回执。明确区分无任务、流程完成、已提交、受阻、结果不明等情况。
- 主要代码：`services/python-workflow/src/workflow_jira.py`、`jira_runtime.py`、`jira_routes.py`，以及 MCP、Sidecar 客户端、结果协议、等待处理和配置中心 `JiraRunController`、`static/jira-runs.js`。

### 现有定时任务驱动

- Jira 查询由现有定时任务的触发周期驱动，没有新增独立 Jira 定时拉取器；网页、钉钉单次触发创建一轮。
- Jira 定时触发按当前空闲监督机与执行机组合数批量预约多轮，每轮独立领取一个工单。同一任务定义可以并行处理不同工单，普通 SOP 仍保持原任务单次运行约束。
- 无容量时持久化一次资源等待，后续约每 30 秒扫描重试，重复定时触发合并，不无限堆积。已经通过的本次前置检查在资源等待后复用，不重复执行脚本。
- 修改、停用或删除定时规则会撤销待调度请求。同一任务已有未分配运行时不继续扩批；其他组无法执行的队列不阻塞本组容量判断。
- 批量运行全部纳入提交恢复与终态对账；钉钉主动通知按运行绑定，不覆盖用户当前聊天选择的单项任务。
- 主要代码：配置中心 `DailyTaskScheduler`、`WorkflowRunService`、`TaskLaunchStore`、`TaskScheduleStore`、`TaskRunRepository`；网关 `jira_routes.py`。

## 后续排障及已修复问题

### 网关持续报数据库字段缺失

- 实际证据：测试网关已经监听端口并完成启动，但 Jira 账号清理任务持续报 `no such column: j.cleanup_attempted_at`；只读检查确认已有 Jira 表缺列。当时测试库没有工作流记录。
- 原因：只有 `CREATE TABLE IF NOT EXISTS`，不能为已存在的表自动补列。
- 修复：在写事务内检查并增加可空列，保留已有领取记录、运行快照和清理状态；回归测试覆盖升级及重复初始化。
- 已正常重启测试网关，确认字段自动补齐，Jira 台账接口返回 HTTP 200，观察超过 35 秒未再出现该异常。没有手动清表、删库或绕过机器占用保护；正式服务未操作。

### 配置中心停留在“正在检查网关…”

- 实际证据：测试配置中心 `/api/gateway/ready` 返回 HTTP 200、`ready: true`；HTML 与所有引用脚本均正常返回。
- 代码发现：直接进入 Jira、分组、定时任务或 MCP 菜单时跳过网关检测，原定时刷新也不覆盖这些页面。分组数据加载较慢时，其他页面的检测也可能被延后。
- 修复：将侧栏网关检测移到公共页面加载和可见页面刷新流程，独立于业务数据加载；每 10 秒检查，切回页面立即检查，失败显示不可用，恢复后更新正常。移除各菜单重复触发，更新脚本缓存版本。
- 已确认运行中的测试配置中心提供修复后的 HTML 与脚本，无需为本次静态资源修复重启。浏览器工具无法访问页面，未直接验证用户浏览器画面；没有把接口验证表述为浏览器验收。
